# Чек-лист лабораторной работы № 2
## Архитектура и модель данных

**Тема проекта:** Информационная система учёта и обработки заявок на устранение простоев насосного оборудования.

### 1. Архитектура системы

- [ ] Определены основные части системы: frontend, backend и база данных.
- [ ] Определены используемые технологии: Vue 3, ASP.NET Core, C# и PostgreSQL.
- [ ] Описано взаимодействие frontend и backend через HTTP-запросы.
- [ ] Определён базовый адрес API: `/api/downtime-requests`.

### 2. Модель данных

- [ ] Определены основные сущности: `DowntimeRequest`, `Pump` и `User`.
- [ ] Для сущностей определены первичные ключи (PK).
- [ ] Для связей между сущностями определены внешние ключи (FK).
- [ ] Для заявки предусмотрены поля: `id`, `number`, `title`, `description`, `status`, `pumpId`, `createdByUserId`, `assigneeUserId` и `createdAt`.
- [ ] Определены статусы заявки: `New`, `InProgress`, `Closed`, `Cancelled`.
- [ ] Данные о насосах и пользователях вынесены в отдельные сущности.
- [ ] Название насоса не дублируется в каждой заявке: для связи используется `pumpId`.

### 3. Проверка третьей нормальной формы (3НФ)

- [ ] В `docs/data-model.md` добавлен отдельный раздел «Проверка 3НФ».
- [ ] Объяснено, почему данные о насосах хранятся в сущности `Pump`, а данные о пользователях — в `User`.
- [ ] Объяснено, почему в `DowntimeRequest` используются внешние ключи, а не повторяющиеся названия насосов и имена пользователей.
- [ ] Приведён пример: при переименовании насоса достаточно изменить одну запись в `Pump`, а не редактировать все связанные заявки.
